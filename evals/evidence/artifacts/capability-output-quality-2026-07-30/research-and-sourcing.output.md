## 迁移调研结论

项目存在明确的停服迁移风险：按材料 A，旧 API 将于 **2026-09-01** 停止；材料 B 显示依赖锁定文件仍解析到旧客户端 **2.4.0**。因此，应将迁移列为停服日前必须完成的事项。

但现有证据只能证明“依赖仍锁定旧客户端”，不能证明：

- 项目代码实际调用了旧 API；
- 生产构建或运行环境正在使用该客户端；
- 新 API、替代客户端及其兼容性方案已经确定。

建议的最小迁移工作包：

1. 盘点旧客户端的真实调用点、构建入口与生产部署依赖。
2. 获取并确认目标 API/客户端的迁移说明、认证方式、请求响应差异和弃用兼容策略。
3. 完成适配改造与回归验证，重点覆盖鉴权、核心请求、错误处理和降级路径。
4. 在停服日前完成生产切换，并移除旧客户端依赖或确认其不再进入运行产物。

当前阻断点是：未提供新 API 的目标版本、迁移文档内容、项目调用点和生产运行证据。因此，不能安全判断改动范围、工期或是否可直接升级版本。

证据边界：

- 材料 A（用户提供前提，标注日期 2026-06-01）：旧 API 于 2026-09-01 停止。
- 材料 B（用户提供前提）：`package-lock` 显示旧客户端版本为 2.4.0；lockfile 仅能证明依赖解析/锁定状态，不能单独证明实际调用或生产运行状态。
