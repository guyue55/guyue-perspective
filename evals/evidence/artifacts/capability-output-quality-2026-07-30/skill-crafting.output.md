## 建议设计：`debugging-mindset / 首个失败测试闭环`

**核心工作**  
从构建日志中锁定首个真实失败测试，以最小证据定位模块、完成定向验证与修复回归，最后运行全套测试。

**正向触发**

- “根据构建日志修第一个失败测试”
- “定位 CI 首个失败并跑定向测试”
- “修复测试后跑全套”

**负向触发**

- 仅解释一段错误日志，不要求执行闭环
- 新功能开发、性能优化、CI 配置设计
- 没有构建日志或可复现失败证据却要求猜测性修复

**稳定输入**

- 构建日志或失败测试原始输出
- 当前代码版本与工作区状态
- 项目测试命令映射：全套命令、按文件/用例定向命令、测试产物位置
- 修复授权与运行预算

**交付产物**

- 首个失败测试：名称、原始报错、日志证据位置
- 对应模块：测试文件、实现文件、定位依据
- 定向测试命令与结果
- 最小修复说明及变更范围
- 全套测试结果，或明确失败/阻断原因

**执行合同**

1. 读取日志，只认首个确定失败；后续连锁失败不作为本轮目标。
2. 用测试名称、堆栈、导入关系或项目映射定位模块；无法唯一定位时停止，不猜改。
3. 先运行失败测试的定向命令，确认当前源码仍可复现。
4. 证据明确后，只修复该失败对应的最小代码集。
5. 重跑定向测试；通过后运行全套。
6. 全套失败时，区分“原首个失败已修复”与“出现新的首个失败”，不把新故障伪装成回归失败。

**停止条件**

- 日志缺失、被截断，或没有可识别的首个失败
- 测试与模块无法建立可验证映射
- 缺少定向或全套测试命令
- 定向测试无法复现，且无法排除旧构建产物/环境差异
- 修复后定向测试仍失败：输出新证据并停止，禁止盲目多轮改动
- 未获写入授权时，仅交付诊断与复现命令

**副作用边界**

- 读取日志、定位和测试可在授权范围内执行。
- 代码修改必须有明确写入授权。
- 不自动重试、重启服务、改 CI 配置、提交、推送或发布。

**实现拆分**

- `debugging-mindset`：证据门、首失败优先、模块定位、修复边界、停止规则。
- 项目适配脚本/配置：从日志提取候选失败、将测试文件映射为定向测试命令、执行全套。
- CI：仅校验确定性不变量，例如日志解析格式、测试命令映射存在；不承担根因判断。

**评测合同**

| 场景 | 预期行为 |
|---|---|
| 构建日志含多个失败 | 只处理首个确定失败 |
| 首个失败可映射到测试与实现模块 | 先定向复现，再最小修复，再全套 |
| 日志截断或无测试名 | 明确阻断并索取完整失败段 |
| 定向测试不复现 | 检查源码/构建产物新鲜度后停止 |
| 修复后全套出现新失败 | 标记原失败已通过，报告新的首失败 |
| 用户要求“直接改一下试试” | 拒绝猜测性修复，要求失败证据 |
| 仅需解释报错 | 保持在普通诊断，不强行进入闭环 |

当前成熟度应为 `candidate`：复用价值已成立，但还缺少项目级测试命令映射、三次真实样本中的失败分支，以及一次未参与设计的留出回放。最小下一步是提供一份脱敏构建日志、该项目的“定向测试/全套测试”命令和一个历史失败样本，用于验证该流程能稳定解析、路由和停止。
