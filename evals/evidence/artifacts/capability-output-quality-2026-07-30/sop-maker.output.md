# SOP：修复服务迁移后 Nginx upstream 端口滞留导致的 API 502

## 适用场景

服务已从 `8080` 迁移至 `8081`，API 经 Nginx 反向代理访问返回 `502`，且确认 Nginx 的实际 upstream 配置仍指向 `8080`。

不适用于未确认服务端口迁移、非 Nginx 代理、服务自身不健康或非 `502` 的故障。

## 已验证的成功链路

1. 将 Nginx upstream 目标端口从 `8080` 改为 `8081`。
2. 执行 `nginx -t` 并通过。
3. 按环境既有方式 reload Nginx 并成功。
4. 执行 `curl /health` 并通过。

## 执行前阻断

以下信息未明确时，禁止修改配置：

- 实际生效的 Nginx 配置位置及对应 upstream 配置项。
- 服务迁移至 `8081` 的确认来源。
- 本环境批准的 Nginx reload 操作。
- `/health` 的实际请求目标及成功判定标准。

> 已知证据只说明 `curl /health` 通过，未提供请求地址、状态码或响应体；执行时必须记录，不能自行补写。

## 操作步骤

1. 确认故障符合适用场景，并记录 API 的 `502` 证据与发生时间。
2. 定位实际生效的 Nginx upstream 配置，确认其中目标端口为 `8080`。
3. 仅将该 upstream 的目标端口修改为 `8081`；不得同时改动协议、主机、路径或无关路由。
4. 执行：

   ```bash
   nginx -t
   ```

   只有校验通过才可继续。

5. 使用本环境既有、已获批准的方式 reload Nginx。
6. 对已登记的健康检查目标执行：

   ```bash
   curl <health-check-target>/health
   ```

7. 确认健康检查通过后，记录本次变更与验证证据，关闭本分支故障。

## 异常处理

| 现象 | 处理 |
| --- | --- |
| 无法确认实际生效配置 | 停止修改，交由配置或平台负责人确认配置来源。 |
| `nginx -t` 未通过 | 不执行 reload；保留完整输出，修正配置后重新校验。 |
| reload 失败 | 停止重试，保留操作结果，按现有变更恢复流程交由配置负责人处理。 |
| reload 后 `/health` 未通过 | 不将端口改回 `8080`；收集健康检查结果并转服务负责人继续排查。 |
| API 仍为 `502` | 本 SOP 已验证的端口滞留分支不成立或未完全生效；保留配置、测试和 reload 证据后升级排障。 |

## 回退边界

本次故障的根因是 upstream 仍指向 `8080`，因此不得仅为“回退”而恢复为 `8080`。只有服务已明确恢复监听 `8080`，且服务负责人授权时，才可走独立变更流程。

## 完成定义与证据

必须同时具备：

- upstream 端口已由 `8080` 更新为 `8081`。
- `nginx -t` 通过的原始输出。
- reload 成功记录。
- `/health` 请求目标、执行时间、原始结果及通过判定。
- 故障 API 不再返回本次 `502` 的验证记录。

## Loop Contract

- **目标**：快速消除服务端口迁移后，反向代理仍指向旧端口造成的 API 不可用。
- **稳定输入**：迁移端口确认、实际生效配置、健康检查目标、Nginx reload 授权方式。
- **循环体**：确认场景 → 修改单一 upstream 端口 → `nginx -t` → reload → 健康检查 → 留存证据。
- **检查器**：Nginx 配置校验与健康检查结果；两者均通过才算完成。
- **停止条件**：配置来源不明、校验失败、reload 失败或健康检查失败即停止并升级。
- **预算上限**：每次事件仅允许一次受控端口变更；失败后不得盲目重试或扩大改动范围。
- **验证资产**：变更前后配置片段、`nginx -t` 输出、reload 记录、健康检查原始结果。
- **沉淀出口**：若同类故障重复出现，将端口迁移检查加入服务发布或迁移的 CI/发布门禁。
